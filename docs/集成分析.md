## 1. 结论摘要

- **MindSpeed Core 是训练加速引擎**：负责让 Megatron 类大模型训练在昇腾 NPU 上运行，并提供并行、通信、重计算、融合算子、显存和性能优化等能力。
- **MindSpeed Agent 是工程助手和能力调度层**：理解用户问题，判断目标仓库和训练后端，选择 Skill 或 MCP 工具，组织模型分析、配置生成、代码修改、测试和诊断。
- 配置校验及 Rank 矩阵页面适合把配置解析、规则校验、拓扑计算等确定性逻辑抽成一个 MCP Server，再由 MindSpeed Agent 的 Skill 调用。
- MCP Server 可以只有一个。建议拆细的是 Server 内部的 Tool 接口，而不是部署很多个 MCP 服务。
- 页面与 MCP 应共用同一套无界面的 `config-core`，避免浏览器规则和 Agent 规则逐渐不一致。

## 2. MindSpeed Core 与 MindSpeed Agent 的分工

当前官方仓库名称是 MindSpeed，官方说明中的 MindSpeed Core 指其核心训练加速能力，并不是本生态目录中的另一个独立仓库。

| 对比项 | MindSpeed Core | MindSpeed Agent |
| --- | --- | --- |
| 通俗比喻 | 汽车的发动机和变速箱 | 导航、维修技师和任务调度中心 |
| 核心职责 | 在昇腾 NPU 上执行并加速训练 | 理解需求，选择 Skill 和工具，生成方案并组织验证 |
| 处理内容 | TP、PP、CP、EP、通信、重计算、融合算子和性能优化 | 模型分析、迁移、配置生成、代码修改、测试和诊断 |
| 是否处于训练热路径 | 是 | 通常不是 |
| 典型输入 | 模型、训练参数、集群和并行配置 | 自然语言需求、代码仓、配置、日志和 Profiling 数据 |
| 典型输出 | 实际训练行为和性能 | 配置建议、代码、报告、验证脚本和诊断结论 |

MindSpeed Agent 的整体关系可以理解为：

```text
Plugin：确定能力域
   ↓
Agent：拆解和编排任务
   ↓
Skill：提供领域知识和操作流程
   ↓
MCP Tool：执行稳定、结构化、可复用的计算或操作
```

## 4. 推荐架构

```text
MindSpeed / MindSpeed-LLM 源码与版本化规则
                    ↓
        config-core 确定性计算库
                    ↓
       ┌────────────┴────────────┐
       ↓                         ↓
一个 MCP Server             HTML 可视化页面
多个结构化 Tool             Rank 矩阵与交互
       ↑
MindSpeed Agent + Skills
理解问题、补齐信息、调用工具、解释结果、组织实机验证
```

建议遵循以下边界：

- Rank 编号、整除约束和配置转换由确定性代码完成，不交给大模型临时推算；
- 页面负责交互和绘图，不让 MCP 操纵 DOM；
- Agent 负责理解用户意图和解释结果，不复制一份规则实现；
- 规则结果带上 MindSpeed 版本、规则版本、假设和证据来源；
- 纯计算与会启动 NPU 训练的操作明确分开。

生成和第 7 项 NPU 实机验证不在第一版范围。五个 Tool 同时返回文本、结构化结果和
同一个 MCP App 界面资源，界面按工具类型展示校验卡片、Rank 表格、修复差异、字段
映射或容量条形图。

### 评估口径：是否已经接入 Agent 能力

上表描述的是**目标方案**，不是当前已经完成的集成。评估分成两层：

| MCP Tool | 未接入 Agent Skill 时 | 接入 Agent Skill 后 |
| --- | --- | --- |
| 1～4：解析、校验、拓扑、修复 | 直接复用 `config-relation-plane` 的确定性规则即可实现，是 MCP 基础层 | Agent 可以识别目标框架、理解“哪些字段不能改”等自然语言约束，并解释结果 |
| 5：配置生成 | 可以根据表单生成候选 YAML 和参数片段 | Agent 可按 MindSpeed-LLM MCore、FSDP2 或 Bridge 选择模板，并补齐框架特有字段 |
| 6：容量估算 | 可以按页面现有口径给出理论估算 | `llm-model-analysis` 或 `fsdp2-model-analysis` 可从真实模型补齐结构、参数量和分片信息，提高估算可信度 |
| 7：NPU 验证 | MCP 只能定义工具接口，无法凭页面表单完成实机验证 | 需要训练验证 Skill、远端环境和明确授权，才能启动训练并收集结果 |

因此，“config-relation-plane 覆盖完整”只表示页面信息足够支持该 MCP Tool 的基础确定性能力，不表示该工具已经开发完成，也不表示 Agent Skill 已经接入。

所有工具建议返回统一的结果信封，例如：

```json
{
  "schema_version": "1.0",
  "rule_version": "mindspeed-x.y",
  "valid": false,
  "errors": [],
  "warnings": [],
  "topology": {},
  "suggestions": [],
  "assumptions": [],
  "confidence": "theoretical"
}
```

## 6. 为什么不只设计一个大工具

### 先区分两个概念

- **MCP Server**：一个可以部署和连接的服务。
- **MCP Tool**：Server 对外提供的一项具体能力。

因此推荐方案不是部署七个 MCP Server，而是：

```text
1 个 mindspeed-config-mcp Server
└── 6～7 个职责清楚的 Tool
```

### 技术上完全可以只有一个 Tool

例如只提供：

```text
analyze_training_config(action, config, options)
```

然后用 `action=parse/validate/topology/fix/generate/run` 区分行为。这个设计能工作，适合快速原型，但长期会出现几个问题：

1. **只想校验时也容易触发不需要的步骤**，输入和输出会越来越大；
2. **权限边界不清楚**，纯计算和启动远端训练混在一个入口里风险较高；
3. **失败位置不清楚**，难以判断是解析失败、规则失败还是远端运行失败；
4. **复用困难**，网页只需要拓扑 JSON，却不得不理解一个巨大的综合返回值；
5. **测试困难**，每改一项功能都可能影响整个大工具；
6. **Agent 不容易选择最小动作**，也不利于展示清晰的操作过程。

### 推荐折中方案

内部保留细粒度 Tool，同时对用户提供一个高级工作流入口：

```text
用户：分析这份配置，发现问题就给修改建议，但不要运行。
  ↓
Agent / analyze_config 工作流
  ├── parse_training_config
  ├── validate_parallel_config
  ├── compute_rank_topology
  └── suggest_config_fixes（仅在需要时调用）
```

用户感受到的是“一次分析”，系统内部仍保持可组合、可测试、可审计。`validate_on_npu` 应继续作为独立且有权限控制的工具，避免一句普通的“看看配置”意外启动训练任务。
