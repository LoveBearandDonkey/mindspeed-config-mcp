# MindSpeed 配置 MCP：目标用户使用流程与改造方向

> 本文描述面向已打开 IDE 的模型开发者的**目标体验**，不是当前功能清单或交付承诺。场景按预计使用频率和任务紧迫度排列；排序是产品假设，仍需用户访谈和使用数据验证。

用户可以点名使用 MindSpeed 配置 MCP、主动打开工作台，也可以只提出训练任务，由 Agent 在需要配置分析时调用 MCP。工具引用和文件引用的写法仅是对话示意，具体入口由 IDE 决定。**分析结果不以打开网页为前提**：简单问题优先在对话中回答，需要探索和可视化时再打开界面。

## 一、V2版用户使用流程

下表“当前用 MindStudio Agent”一列以 `msagent` 为例：在目标训练工程目录运行，按其 [MCP 配置说明](https://mindstudio-docs-master.readthedocs.io/zh-cn/latest/msagent/docs/zh/user_guide/configuration-and-extension/)接入本项目的 MCP 服务，并确认所选 Agent 能调用相应工具。本项目当前源码提供[九个只读计算工具和七个界面入口](../README.md)；MindStudio Agent 默认内置的性能分析 MCP 不能替代本项目的配置 MCP。表中的“能实现”指可用现有能力完成任务，不表示已有全自动的一体化流程。V2 目前是目标设计，本表未提供与现行流程的用户测试或端到端对照；下列加粗结论区分代码或官方文档支持的能力与待验证的体验收益，不能代替真实端到端验收。

### 开始提问前：成员核对表

| 常见问题 | 成员要做什么 | 怎样确认可以提问 |
| --- | --- | --- |
| **1. 腾讯云已部署，我的电脑就能用 MCP 吗？同事怎么接入？** | 云端只部署一次；每位成员都要在自己使用的 MCP 客户端中配置 **V2** 地址 `https://42.192.111.92/mindspeed-config-v2/mcp`，并通过受控渠道取得 V2 Bearer token。凭据放在本机用户环境变量或客户端支持的安全凭据位置，不写进聊天、Git 或项目配置。同事不需要 SSH、Docker，也不需要克隆本 MCP 仓库。参见 [V2 安装说明](../deploy/README-v2.md) 和 [团队访问方式](./团队成员简易MCP访问方式.md)。 | `https://42.192.111.92/mindspeed-config-v2/health` 返回 `status: ok` 只证明云端入口可达；还要在**将要提问的 Agent 会话**中看到 `mindspeed-config-v2`，并成功调用一次 `parse_training_config`。只看到服务登记、浏览器页面或健康检查，都不算完成 Agent 接入。 |
| **2. 必须在本 MCP 工程里提问吗？** | 不必。在 IDE 打开**待分析文件所在的训练工程**，或确保 Agent 有权限读取给出的绝对路径；让 Agent 读取启动脚本及相关模型配置的实际内容，并说明使用的是磁盘已保存版本还是显式提供的未保存编辑内容。MCP 服务只接收 Agent 传入的文本，不能根据你电脑上的文件路径去腾讯云读取文件。 | 在工具调用前确认 Agent 读到了正确文件和版本；路径在其工作区之外时，先确认该客户端确实允许访问。对本章第 1 场景，至少能同时读取启动脚本与模型配置。 |

**Codex 接入示例（PowerShell）：**先通过系统设置或受控凭据管理方式把 V2 token 保存为本机用户环境变量 `MINDSPEED_CONFIG_V2_MCP_TOKEN`，重新启动 IDE/终端后运行以下不含 token 明文的命令。`codex mcp list` 只能确认登记；还须在会话里完成一次工具调用。[Codex MCP 官方说明](https://developers.openai.com/codex/extend/mcp)

```powershell
codex mcp add mindspeed-config-v2 `
  --url https://42.192.111.92/mindspeed-config-v2/mcp `
  --bearer-token-env-var MINDSPEED_CONFIG_V2_MCP_TOKEN
codex mcp list
```

**Claude Code 接入示例（PowerShell）：**同样先让启动 Claude Code 的进程能读取上述环境变量，再以 user scope 登记，随后运行 `claude mcp list` 并在会话中用 `/mcp` 检查连接。JSON 中的 `${MINDSPEED_CONFIG_V2_MCP_TOKEN}` 由 Claude Code 从环境变量展开，不是 token 明文。[Claude Code MCP 官方说明](https://code.claude.com/docs/en/mcp)

```powershell
claude mcp add-json mindspeed-config-v2 '{"type":"http","url":"https://42.192.111.92/mindspeed-config-v2/mcp","headers":{"Authorization":"Bearer ${MINDSPEED_CONFIG_V2_MCP_TOKEN}"}}' --scope user
claude mcp list
```

**版本核对：**当前源码基线为九个计算 Tool 和七个界面入口。每次发布后、开始场景验收前，都应在实际连接的 V2 服务上重新枚举工具；若远端少于 16 个入口，应先核对部署提交，不能把“本地九项已改完”直接视为“云端已更新”。

## 二、原生 MindSpeed-Agent 使用流程

<strong>一句话：</strong>先下载/克隆仓库，在命令行安装 MindSpeed-Agent 插件 → 在要处理的模型仓库中使用 Codex 或 Claude Code 提问 → Agent 按任务选择本仓技能 → 返回分析结论；若用户要求修改代码，Agent 在模型仓库中修改文件并展示差异与验证结果。

##### 如何安装
 `install.bat` 的使用路径：本地没有 MindSpeed-Agent 时，先在 CMD 运行 `git clone https://gitcode.com/Ascend/MindSpeed-Agent.git`、`cd MindSpeed-Agent`；已有本地副本则直接进入其根目录。<strong>使用该脚本需要本地仓库</strong>；其中 `install.bat codex` 就是把插件注册并安装到 Codex 的步骤。开发时只需在 IDE 打开<strong>目标模型仓库</strong>，不必同时打开 MindSpeed-Agent 仓库。Codex、Claude Code 的插件市场命令也支持远程仓库来源，但本仓领域插件的技能目录由本地安装脚本生成，此处以脚本安装路径为准。

##### 典型使用方式

- <strong>Codex：</strong>克隆 MindSpeed-Agent 到本地 → 在该仓根目录运行 `install.bat codex` → 用 IDE 打开目标模型仓库，并在该仓运行 `codex` → 提问 → 补齐 Codex 询问的信息或按提示安装所需领域插件 → Codex 返回结论或修改建议 → 用户若要落实建议，在同一会话继续说“请按上述建议修改当前仓库” → Codex 修改目标仓库文件 → 用户查看文件差异和实际完成的验证。没有补充信息或安装提示时，直接进入返回结论的步骤；用户也可以在第一次提问时直接要求修改。
- <strong>Claude Code：</strong>克隆 MindSpeed-Agent 到本地 → 在该仓根目录运行 `install.bat claude-code` → 用 IDE 打开目标模型仓库，并在该仓运行 `claude` → 提问 → Claude Code 返回结论或修改建议 → 用户继续要求应用建议（也可在第一次提问时直接要求修改）→ Claude Code 修改目标仓库文件 → 用户查看文件差异和验证结果；信息不足或缺少领域插件时，先按提示补齐。
- <strong>DSH(DeepSeek Harness)：</strong>克隆 MindSpeed-Agent 到本地 → 在该仓根目录运行 `install.bat dsh`（技能投影到本仓 `.dsh/skills`）→ 在<strong>MindSpeed-Agent 仓内</strong>运行 `dsh web` → 提问时给出目标模型仓库的路径 → 得到结论或建议；如需修改该仓文件，继续要求应用建议，并让 DSH 能访问目标仓库路径。此安装方式目前不会把技能自动安装到另一个模型仓库。

##### 典型疑问

- <strong>路由从哪里来、何时使用：</strong>本仓自带 `skills/common/common/ecosystem-routing/SKILL.md`，随基础插件安装。宿主 Agent 根据技能描述判断请求是否涉及 MindSpeed 生态仓库、模型或开发任务；相关时可调用它，再结合 `catalog/` 判断目标仓库和任务类型，有歧义会先询问。关键词有助于识别任务，但不是每条回答都调用路由 Skill；用户也可明确要求按它路由。
- <strong>领域插件为什么可能“缺少”：</strong>本仓 `plugins/` 中有 `mindspeed-llm`（LLM 训练）、`inference-model-optimize`（推理优化）、`ops`（算子开发）、`doc-agent`（资料工作）等插件的代码，但克隆仓库不等于将这些插件安装到宿主。`install.bat` 不带第二个参数时默认选择 `core`：`install.bat codex` 安装基础插件 `mindspeed-agent`；`install.bat claude-code` 安装基础插件，脚本还额外尝试安装 `veomni-agent`，但<strong>不会安装前述四个领域插件</strong>。所以“缺少”指任务需要的那个插件尚未安装到当前宿主。按需安装是上述使用路径的<strong>补充步骤</strong>：收到提示后，在同一个 MindSpeed-Agent 本地仓库运行相应命令，例如 `install.bat codex mindspeed-llm` 或 `install.bat claude-code mindspeed-llm` → 新开宿主会话 → 在目标模型仓库重新提出原任务。首次安装时也可指定领域插件；想一次安装全部领域插件，可用 `install.bat claude-code all` 或 `install.bat codex all`。DSH 则需把对应技能投影到 `.dsh/skills`。

>上述“继续说”是用户在同一会话的输入框再发一句话，不必复制建议文字，也没有自动把建议填进输入框的步骤。咨询类问题返回结论或建议；明确要求修改代码时，宿主 Agent 才会读取并修改<strong>目标模型仓库</strong>中的文件，随后报告改了哪些文件、文件差异和实际完成的验证。基础路由只负责确定调用方向，不能把“已给出路由建议”当成“代码已修改”。

## 二、贯穿所有场景的交互原则

- **一份分析，多种呈现：**默认给简短文字结论；需要复核时给完整报告或结构化数据；需要探索关系时打开交互界面。呈现形式由任务和用户选择，不改变计算口径。
- **先结论，后证据：**首屏或首条回复先说是否存在阻断问题、最重要的风险和下一步动作；公式、全部字段、Rank 明细按需展开。
- **源头可追溯：**标明分析所用文件、版本、用户约束和假设；文件或输入改变后，旧结论不再冒充当前结论。
- **区分确定性：**静态规则冲突、理论容量风险、性能调优假设和实测结果分别标记；不以“通过校验”代替“已验证训练可运行”。
- **分清责任：**MCP 提供确定性的配置计算与证据；Agent 组织跨文件、跨领域任务及文件修改；用户决定目标与不可变约束。训练启动和对外发送属于独立操作。

第 1 项的文本摘要由纯计算核心的 `quick_assessment` 生成：先给结论，再给首要问题及来源、下一步和局限；完整诊断继续保留在 `structuredContent`。第 2 项中，`parse_training_config` 返回源文本 SHA-256；把该 `source_snapshot` 随完整配置传给 `suggest_config_fixes`，候选的 `changes` 仅是建议，不表示文件已修改。Agent 修改并重新读取源文件后，向 `review_config_change` 传入修改前后文本、锁定字段、分析时摘要和选中候选的差异；复查结果明确指出过期基线、锁定字段变化、候选不符、缺项与修改后的静态校验结果。工具本身不按路径读取或写入文件。

第 3、4 项的当前实现：`open_config_workbench` 可选接收 `objective` 和 `source`（训练配置文本及可选模型结构文本）。内嵌 App 将来源直接填入导入区并调用现有解析 Tool；用户核对补齐方案后才应用到工作台。HTTP 服务配置 `MCP_BROWSER_PUBLIC_ORIGIN` 后，Tool 同时返回独立 Web 链接。链接的片段仅含一次性交接码，配置正文存放于服务端短时内存；浏览器登录后领取，领取即作废，10 分钟后过期。独立静态页和未配置公网 Origin 的服务不提供该交接链接。工作台概览显示本次来源、目标、校验结论、首要依据和下一步，初始以导入为主操作；原表单留在当前视图，Rank/容量画布在宽屏默认可见、在窄面板纵向排列。概览与详细结果共用 `structuredContent`，页面不计算另一套结论。目标宿主的内嵌渲染、自动选用 Web 和窄面板操作仍须实测。

第 7～9 项的边界：性能瓶颈摘要由 Agent 从本次运行的 Profiling 或日志取得，本工具不读取远端数据，也不把瓶颈类别当成已证实的配置归因。报告生成只汇总已有结构化结果；当报告来源 SHA-256 与修改复查的 after 摘要一致时，才能称为“按提交的修改后文本复查”，磁盘写回仍由 Agent 确认。页面快照保存在浏览器的当前 Origin，按用户指定的工程名称隔离；源摘要和页面配置指纹是两个版本标记，恢复快照只改变页面试验值，不修改源文件。目标 IDE 中的持久化和工程身份仍须实测。

**UI 承载策略：**内嵌 MCP App 是支持 MCP Apps 宿主中的首选体验，由工具关联 `ui://` 资源并在聊天沙箱中渲染；配套 Web 应用用于宿主不支持内嵌 UI、需要更大工作区或独立访问的场景。Web URL 由工具返回时，不承诺仅凭链接即可自动打开；是否自动打开取决于 Agent 和宿主是否执行浏览器操作，否则由用户点击进入。两种方式只负责交互与呈现，业务规则仍以 `config-core` 为唯一事实来源。

### 现行版本保留与新方案试验

1. **先固定可恢复基线：**把当前可用状态提交为独立版本，建立不会随开发分支移动的受保护标记；连同完整源码、依赖锁文件、可运行发布包、已打包页面、代表性输入与预期结果、不含密钥的部署说明归档，并记录校验值。保留远端仓库副本和独立备份，不能只留下截图或单个 HTML 文件。
2. **再隔离开发：**从基线开新分支和独立工作树。旧版继续使用固定源码与产物；新版使用不同的构建目录、预览地址和发布标识，避免预览、打包或部署脚本覆盖旧版。
3. **双轨验收：**用同一批典型配置比较旧版与新版的解析、校验、Rank、修复和容量结果；对故意改变的规则列出来源依据与差异。另按本文六条用户流程检查对话、文件修改和界面体验，再逐步让目标用户试用。
4. **切换与回退：**验收完成后才把默认入口指向新版；旧版代码、产物和启动方式继续保留。若新版出现严重回归，可直接切回已固定的旧版，不依赖现场重新拼装。

**删减原则：**不要把每个计算 Tool 都做成一个必须经过的独立页面；不要在首屏重复展示原文、全部字段和完整公式；保留可交互的 Rank 画布；不要保留没有实际行为的“应用”“导出”按钮。复杂度只在用户需要判断、比较或复核时逐级展开。
